# REFLECTION（项目反思）

## 一、项目缘起与目标

这个项目最初的方向是模仿 Claude Code，做一个用 Rust 实现的编码智能体执行框架。项目从零实现了 harness 内核，包括主循环、工具系统、四层护栏、反馈闭环、记忆与子 agent 委派，核心代码不依赖现成的 agent 框架。

交互设计上借鉴了 Claude Code 的一部分设计，比如 `/resume` 等一系列会话命令、全局配置与局部配置的分层。同时，为了能够嵌入脚本一次性执行任务而不用交互，另外设计了两个管道模式（TUI 与纯文本）：除高风险操作触发护栏需要人工批准外，其余流程不需要用户操作；审批力度也可以通过命令行参数调整，从而减少触发护栏打断的频率。

## 二、Superpowers 的利与弊

Superpowers 带来了一些实实在在的便利。在项目暂时不清晰的时候，brainstorming 的连续追问完善了空白，比如为什么做这个、给谁用、危险动作是什么、哪个维度是重点。追问能把问题提前暴露出来，而不是等到代码写完再返工。writing-plans 把工作拆成带验证步骤的任务，是让智能体长时间推进而不脱轨的关键。

但另一方面，这套流程对小改动是明显的负担。项目后期大量迭代是类似“修一个审批块的清除时机”这种五分钟级别的小修复，按完整流程走一遍，沟通与 token 消耗远大于改动本身的价值。这个项目里我的实际做法是：大功能走完整流程，小改动在前提明确时直接修。按改动规模决定流程深度，是我认为 Superpowers 实践里最重要、但文档没有明说的部分。

## 三、TDD 在 AI 协作中是阻碍还是放大器

我原先觉得 AI 写代码已经很快，再强调 TDD 可能只是增加步骤。真正做下来后，我的看法变了：AI 的优势恰好是改得快，而测试能让这种速度不至于变成失控。尤其在项目后期，一个看起来很小的界面或配置修改也可能影响之前的行为。先把问题稳定地复现出来，再交给 AI 修改，沟通会更明确，我也更容易判断它到底修好了没有。

不过，TDD 对我来说并不是必须照搬的固定仪式。需求还在变化、接口尚未定型时，过早写得太细，测试反而会把临时设计固定住，之后每改一次结构都要跟着维护。这个项目中更适合我的做法是：对明确的 bug 先写回归测试，对探索中的功能先确定行为边界，等方向稳定后再补测试。测试最有价值的地方不是数量多，而是它能替我记住那些已经踩过的坑。

## 四、task 颗粒度与 subagent 工作流

我逐渐发现，task 的合适大小不是看代码行数，而是看它能不能独立说明目标、独立验证结果。拆得太细，AI 每走一步都要重新理解上下文，最后大量内容都花在交接上；拆得太粗，又容易在长时间执行中偏离目标，而且很难判断问题出在哪一步。比较有效的拆法，是让每个任务都有一个用户能够观察到的结果，同时把关系紧密的改动放在一起。

subagent 适合处理边界清楚、彼此独立的工作，但它也很容易制造一种“大家都完成了，所以项目完成了”的错觉。本项目里就出现过模块本身写好了，真正运行时却没有接入主流程的情况。这让我意识到，委派之后最重要的不是收集多少份完成报告，而是检查它们是否真的汇合成一个可用的整体。以后使用 subagent 时，我会更重视最后的集成验证，而不是只看每个子任务是否打勾。

## 五、SPEC / PLAN 对实现的影响

这个项目让我更直观地看到，SPEC 和 PLAN 不只是写给人看的说明，也是 AI 判断优先级的依据。文档里一句含糊的话，未必会让实现完全错误，却可能让开发顺序发生偏差。早期我没有充分说明主要使用方式，结果先完成了相对次要的入口，真正经常使用的交互模式反而在后面补上，随之带来了不少调整。

因此，我现在认为一份好的 SPEC 应该先讲清楚用户最常做什么、什么体验最重要，再描述功能清单；PLAN 则要说明依赖关系和每一步如何验收，而不只是把功能拆成列表。文档也不应该在开工后就被冻结。实际使用中发现理解有偏差时，及时修订比勉强维护“最初计划完全正确”的表象更有价值。让一个不了解背景的人只读文档尝试启动项目，也是检验文档是否可靠的简单办法。

## 六、prompt / context 策略

在 prompt 和 context 方面，我最大的体会是“更多”通常不等于“更好”。一开始很容易把规则、工具说明、历史记录都塞进系统提示词，认为信息越完整，模型表现就越稳定。实际使用中，过多内容会稀释当前任务，真正重要的约束反而不容易被注意到。

后来我把上下文分成了几类：长期稳定的原则放在基础提示中，项目规则随项目加载，具体工具和技能只在需要时提供，当前操作则只附上与判断有关的最近信息。这样做不仅节省上下文，也让用户看到的提示和模型收到的信息更一致。对我来说，context engineering 更像是在安排注意力，而不是单纯扩大输入容量；关键是决定什么信息应该在什么时刻出现。

## 七、凭据与分发

做到项目收尾时，我才真正意识到，“在我的电脑上能运行”和“别人能够使用”之间还有很长一段距离。开发阶段我更关注功能是否实现，到了分发阶段才不得不站在第一次接触项目的人的角度，重新检查安装方式、配置步骤、错误提示和安全边界。很多原本习以为常的本机条件，对其他用户来说都可能不存在。

凭据管理也让我认识到，安全不能只靠一句“不要泄露 key”。程序需要提供相对稳妥的保存方式，也要诚实说明兼容方案和降级方案的局限。分发同样如此：源码、容器和二进制面向的用户不同，说明文档应该让他们都能找到一条清楚的开始路径。这部分工作看起来不像核心功能，却直接决定了项目是一个个人演示，还是一个别人真的可以尝试的工具。

## 八、如果重做

如果重做一次：一是优化护栏，引入 AI 辅助审批。让模型先给出风险评估与建议，减少人工审批的认知负担；二是在一定程度上让管道模式更自动化，比如反馈闭环在测试失败时自动尝试修复而不是停在报告；三是优化 REPL 界面，尤其是子 agent 相关的展示（目前子 agent 运行期间 REPL 无法刷新界面，只能等完成摘要）。另外会把 SPEC 的交互优先级写清楚，避免 REPL 后置的弯路。

## 九、批评对待 Superpowers 方法论

Superpowers 最大的价值，是提醒我不要把 AI 的高产出误当成工程质量。先澄清、再计划、用测试验证、最后复查，这些步骤确实让项目比单纯依靠提示词推进更稳定。尤其当任务较大、会持续较长时间时，有一套共同流程能减少遗漏，也方便人在关键节点重新接管判断。

但我不认为它适合成为不能调整的标准答案。真实需求往往是在使用中逐渐形成的，有些问题只有做出原型后才会出现；如果一开始就要求把所有事情定义清楚，容易得到一份形式完整但并不贴近实际的计划。流程本身也有成本，小修改如果机械地走完所有步骤，反而会拖慢节奏。经过这个项目，我更愿意把 Superpowers 看成一组可选择的工具：复杂、风险高的改动需要完整约束，简单且边界明确的修改可以采用更轻的流程。方法论提供纪律，但什么时候坚持、什么时候简化，仍然需要人的判断。
